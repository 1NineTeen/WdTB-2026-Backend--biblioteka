Praca w zespole

Zespół

  • 3 osoby, jedno repozytorium na GitHubie: fork wkoszela/WdTB-2026-Backend--projectname- przemianowany na WdTB-2026-Backend-<nazwaprojektu> (krok po kroku: LAB 01).
  • Zespół wpisuje się do arkusza zespołów w zakładce swojej grupy: imię i nazwisko, numer indeksu, e-mail każdej osoby oraz link do repozytorium. Repozytorium hostuje jedna osoba z zespołu. Bez wpisu w arkuszu zespół nie jest oceniany.
  • Osoba hostująca repozytorium jest jego właścicielem. Pozostałe osoby i prowadzącego dodaje jako współpracowników (Settings → Collaborators → Add people).

Kto co robi

Nie ma przydzielonych ról. Jedna osoba hostuje repozytorium, a pracę dzielicie na zajęciach według encji, zapytań czy endpointów: każdy pisze kod i każdy robi recenzje u innych.

Przepływ pracy

issue  →  gałąź  →  commity  →  Pull Request  →  recenzja innej osoby  →  zielone „Testy i reguły”  →  merge do main
  1. Issue dla każdej historyjki / pytania inwestora (szablony: New issue → Historyjka / Pytanie inwestora), przypisane do jednej osoby.
  2. Gałąź od main: <nr-issue>-krotki-opis, np. 12-encja-rezerwacji. GitHub tworzy ją z poziomu issue (Development → Create a branch).
  3. Pull Request do Waszego repozytorium (base repository = Wasz fork, nie wkoszela/WdTB-2026-Backend--projectname-), szablon opisu wczyta się sam, Closes #12 w opisie. Mały PR (do ~300 linii) = szybka recenzja.
  4. Recenzja: co najmniej jeden merytoryczny komentarz od innej osoby. „LGTM” to nie recenzja.
  5. Merge tylko przy zielonym sprawdzeniu „Testy i reguły”.

Ustawienia repozytorium na GitHubie (osoba hostująca, LAB 01)

  • Settings → Branches → Add branch ruleset (albo Add classic branch protection rule) dla main: ✅ Require a pull request before merging (1 zatwierdzenie), ✅ Require status checks to pass (wybierzcie „Testy i reguły projektu” po pierwszym przebiegu), ✅ Block force pushes.
  • Settings → General → Pull Requests: ✅ Automatically delete head branches.
  • Issues → Labels: historyjka, pytanie-inwestora.
  • Issues → Milestones: LAB 01 … LAB 07.

Konflikty w Gicie

  • data.sql edytuje cały zespół, więc konflikty są tu najczęstsze. Dopisujcie dane na końcu sekcji swojej tabeli i często mergujcie main.
  • Przed Pull Requestem: git fetch && git rebase origin/main (albo merge main do swojej gałęzi).

Ocena indywidualna

  • Raport Wkład członków zespołu (zakładka Actions → Summary) pokazuje commity i zmienione linie per autor od poprzedniego tagu. To punkt wyjścia do rozmowy, nie ocena.
  • Na ocenie prowadzący wybiera losową osobę i losowy fragment kodu: „wytłumacz”, „zmień”, „dlaczego tak?”.
  • Osoba bez zmergowanego Pull Requesta na danym labie dostaje za ten lab maksymalnie 3.0.

Kiedy zespół się sypie

Jeśli ktoś nie pracuje, zespół zgłasza to prowadzącemu od razu, na zajęciach. Nie ratujcie oceny kolegi własną pracą bez słowa.
