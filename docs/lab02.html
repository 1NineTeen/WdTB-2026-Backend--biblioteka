LAB 02 · Encje i relacje w JPA

Cel: pomysł z LAB 01 zamieniacie w model danych JPA. Hibernate buduje z niego tabele w H2, a plik data.sql wypełnia je danymi startowymi.

Czego się nauczysz: mapowania encji (@Entity, @Table, @Id, @Column), relacji (1:N, N:M, 1:1), enumów i typów liczbowych, czytania SQL generowanego przez Hibernate, wstawiania danych przez data.sql.

B · Encje i relacje (60 min)

Wzorem jest gotowa encja UserAccount w pakiecie account.domain. Swoje encje dodajecie w pakietach pl.wsb.<projekt>.<moduł>.domain, np. pl.wsb.deskhop.booking.domain.

Czego wymagamy od bazy

W bazie musi być… Jak to uzyskać w JPA
aplikacja startuje bez błędów poprawne mapowanie (pierwszy Caused by w logu wskaże błąd)
≥4 Wasze tabele, każda z kluczem głównym @Entity, @Table(name = "…"), @Id + @GeneratedValue
≥4 klucze obce @ManyToOne + @JoinColumn, @OneToOne, tabela łącząca
tabela łącząca dwie inne (N:M) @ManyToMany + @JoinTable albo encja z dwoma @ManyToOne
klucz obcy z UNIQUE (1:1) @OneToOne + @JoinColumn
powiązanie z user_account np. @OneToOne UserAccount account w profilu klienta
kolumna ENUM pole typu enum z @Enumerated(EnumType.STRING)
brak kolumn DOUBLE/REAL kwoty i ilości jako BigDecimal
dane w ≥2 Waszych tabelach (≥3 wiersze) insert w data.sql (część C)

Przykład mapowania

@Entity
@Table(name = "booking")
public class Booking {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)        // N:1 → klucz obcy customer_id
    @JoinColumn(name = "customer_id", nullable = false)
    private Customer customer;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)        // druga strona → booking to encja łącząca (N:M)
    @JoinColumn(name = "offer_id", nullable = false)
    private Offer offer;

    @Column(name = "price", nullable = false, precision = 10, scale = 2)
    private BigDecimal price;                                   // nie double!

    @Enumerated(EnumType.STRING)                                // w bazie 'CONFIRMED', a nie 1
    @Column(name = "status", nullable = false, length = 20)
    private BookingStatus status;

    protected Booking() {                                       // wymagany przez JPA
    }

    public Booking(Customer customer, Offer offer, BigDecimal price) {
        this.customer = customer;
        this.offer = offer;
        this.price = price;
        this.status = BookingStatus.NEW;                        // encja startuje w poprawnym stanie
    }
}

@Entity
@Table(name = "customer")
public class Customer {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @OneToOne(fetch = FetchType.LAZY, optional = false)         // 1:1 → klucz obcy account_id z UNIQUE
    @JoinColumn(name = "account_id", nullable = false, unique = true)
    private UserAccount account;

    @OneToMany(mappedBy = "customer")                           // strona odwrotna relacji z Booking.customer
    private List<Booking> bookings = new ArrayList<>();

    protected Customer() {
    }
}

Na co uważać

  • Właściciel relacji to strona z @JoinColumn (zwykle @ManyToOne). mappedBy stoi po stronie odwrotnej i wskazuje nazwę pola, nie kolumny.
  • @ManyToMany czy encja łącząca? Jeśli połączenie ma własne dane (data, ilość, status), to musi być encja łącząca. Wybór i powód zapiszcie w dzienniku decyzji w PROJEKT.md.
  • Słowa zastrzeżone SQL: tabela user albo order wysadzi aplikację. Użyjcie np. customer_order.
  • Lombok: @Getter jest w porządku. @Data na encjach odpada (pętle w toString, hashCode na relacjach).

C · Dane startowe w data.sql (20 min)

Dopiszcie do src/main/resources/data.sql dane do swoich tabel: co najmniej 3 wiersze w co najmniej 2 tabelach, najlepiej 5–10 w głównych tabelach, z różnymi statusami.

insert into customer (account_id, home_city) values (1, 'Wrocław'), (2, 'Wrocław'), (5, 'Poznań');
insert into offer (title, price, status) values
    ('Biurko przy oknie', 25.00, 'AVAILABLE'),
    ('Sala konferencyjna', 120.00, 'AVAILABLE'),
    ('Biurko w open space', 15.00, 'BLOCKED');
insert into booking (customer_id, offer_id, price, status) values (1, 1, 25.00, 'CONFIRMED');
  • Kolejność ma znaczenie: najpierw tabele, na które wskazują klucze obce (konta, klienci, oferty), potem te, które je wskazują (rezerwacje).
  • Nazwy kolumn bierzecie z @Column(name = …) i @JoinColumn(name = …), a w razie wątpliwości z konsoli H2.
  • Identyfikatory nadaje baza (IDENTITY), więc pierwsze konto z data.sql ma id = 1, drugie id = 2 itd.
  • Sprawdźcie, czy dane mają sens (rezerwacja na wyprzedaną ofertę? cena ujemna?).

D · Konsola H2 (15 min)

  1. Uruchomcie aplikację w IntelliJ (Run na ProjektApplication) i w logach znajdźcie create table … wygenerowane przez Hibernate.
  2. W http://localhost:8080/h2-console sprawdźcie i zapiszcie w opisie Pull Requesta: - jak wygląda tabela łącząca N:M i jaki ma klucz główny, - po której stronie relacji 1:1 jest klucz obcy i skąd wziął się na nim UNIQUE, - jakim typem kolumny Hibernate zapisał enum (co by było przy EnumType.ORDINAL?).
  3. Napiszcie jedno zapytanie z JOIN przez dwie Wasze tabele, np. rezerwacje razem z nazwą klienta.
  4. Zaktualizujcie diagram ER w PROJEKT.md, żeby zgadzał się z tym, co faktycznie powstało.

Pytania kontrolne (losowa osoba z zespołu)

  1. Dlaczego encja potrzebuje konstruktora bezargumentowego i dlaczego może być protected?
  2. Co oznacza mappedBy i co się stanie, gdy zapomnimy go po stronie @OneToMany?
  3. Dlaczego @ManyToOne domyślnie jest EAGER i czym to grozi?
  4. EnumType.ORDINAL vs STRING: pokaż na przykładzie, jak ORDINAL psuje dane.
  5. Dlaczego 0.1 + 0.2 w double to problem dla aplikacji, która liczy pieniądze?
