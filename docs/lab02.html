TeoriaB · Wprowadzenie: tabela ↔ encja, relacje

B1. Encja to klasa, która opisuje tabelę

Na LAB 01 widzieliście w oknie Run polecenie create table user_account. Hibernate wygenerował je z klasy UserAccount. Tak działa JPA: klasa ↔ tabela, pole ↔ kolumna, obiekt ↔ wiersz. Otwórzcie account/domain/UserAccount.java i porównajcie z tabelą w konsoli H2:

Adnotacja Znaczenie W UserAccount
@Entity klasa jest encją: Hibernate tworzy dla niej tabelę nad klasą
@Table(name = "…") nazwa tabeli w bazie (małe litery, podkreślenia) user_account
@Id + @GeneratedValue(strategy = IDENTITY) klucz główny; numer nadaje baza (1, 2, 3…) Long id
@Column(name, nullable, unique, length) nazwa i ograniczenia kolumny email: wymagany, unikalny, 120 znaków
@Enumerated(EnumType.STRING) enum zapisany jako tekst ('ADMIN'), a nie numer pozycji AccountRole role
konstruktor protected bez argumentów wymaga go Hibernate; drugi, publiczny, służy Wam protected UserAccount() {}

B2. Typy kolumn

Dane Typ pola w Javie Uwagi
tekst String zawsze z length, np. 60 lub 120
liczby całkowite, ilości Integer, Long liczba miejsc, sztuk, punktów
kwoty, ceny, oceny dziesiętne BigDecimal nigdy double ani float: 0.1 + 0.2 daje 0.30000000000000004; kolumna precision = 10, scale = 2
data, data z godziną LocalDate, LocalDateTime w data.sql: '2026-11-14', '2026-11-14 18:00:00'
status, typ, kategoria ze stałej listy enum zawsze z @Enumerated(EnumType.STRING)
tak / nie Boolean np. active

B3. Relacje: klucz obcy to pole typu innej encji

W bazie relacja to kolumna z kluczem obcym, np. reservation.table_id wskazuje wiersz w cafe_table. W JPA tę kolumnę opisuje pole typu drugiej encji. Przykład kawiarni z LAB 01:

cafe_table  1 ───< N  reservation  N >─── 1  guest  N >─── 1  user_account
 (stolik)              (rezerwacja)          (gość)             (konto, gotowe)
                            1
                            │
                            < N
                      reservation_extra  N >─── 1  extra
                      (dodatek do rezerwacji:        (tort, kwiaty)
                       rezerwacja + dodatek + ilość)

B4. Konto użytkownika a klient

UserAccount to konto logowania: e-mail, rola, data założenia. Nie dopisujcie do niego numeru telefonu, adresu ani historii zamówień. Osoba korzystająca z Waszej aplikacji (gość, klient, czytelnik, członek klubu, gracz, uczeń) to własna encja z danymi biznesowymi, która wskazuje na konto:

@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "user_account_id")
private UserAccount account;        // null, gdy gość nie ma konta (np. rezerwacja telefoniczna)

Dzięki temu na LAB 06 to samo konto posłuży do logowania, a Wasza encja pozostanie niezależna od mechanizmu uwierzytelniania.

B5. Tabele, które powtarzają się w większości projektów

Z opisów projektów w arkuszu zespołów wynika, że prawie każdy projekt ma ten sam szkielet: osoba (z kontem) korzysta z zasobu lub oferty, a łączy je transakcja ze statusem (rezerwacja, wypożyczenie, zamówienie, zapis). Różnią się tylko nazwy:

Tabela Co przechowuje Kino / wydarzenia Siłownia / zajęcia Biblioteka / wypożyczalnia Sklep / zamówienia
user_account (gotowa) logowanie: e-mail, rola — — — —
osoba → konto imię i nazwisko, telefon, numer karty; @ManyToOne UserAccount Widz Członek klubu, Trener Czytelnik Klient

encja łącząca N:M para + atrybuty; dwa pola @ManyToOne Rezerwacja: Widz × Seans + miejsce Zapis: Członek × Zajęcia + data Wypożyczenie: Czytelnik × Egzemplarz + daty Pozycja: Zamówienie × Produkt + ilość, cena

Ten sam wzór mają pozostałe projekty: hotel lub parking (Zasób → Rezerwacja ← Klient), gry i rankingi (Gracz × Mecz + wynik), magazyn lub zadania (Produkt × Lokalizacja + ilość), dziennik (Uczeń × Przedmiot + ocena).

ZadanieD · Model danych zespołu

Zanim napiszecie kod, narysujcie tabele na kartce (albo w dowolnym narzędziu). Prowadzący podchodzi do zespołów i sprawdza schemat. Punktem wyjścia są rzeczowniki z opisu pomysłu (LAB 01, krok C2) i tabela z części B5.

  1. Lista tabel: 4–6 własnych (poza user_account, R2.01). Przy każdej: kolumny, typy, które kolumny są wymagane.
  2. Strzałki: każda relacja „wiele-do-jednego” to strzałka od tabeli „wiele” do tabeli „jeden”, a w kodzie pole @ManyToOne. Przy strzałce zapiszcie nazwę kolumny klucza obcego: <tabela>_id (R2.04).
  3. Relacja wiele-do-wielu: znajdźcie parę tabel, które łączy coś z własnymi atrybutami (ilość, data, miejsce, wynik). To Wasza encja łącząca: osobna tabela z dwiema strzałkami (R2.05).
  4. Obiekt ze statusem: wybierzcie encję z cyklem życia (rezerwacja, zamówienie, wypożyczenie) i wypiszcie stałe enuma, np. NEW, CONFIRMED, CANCELLED, DONE (R2.07). Kwoty to BigDecimal (R2.08).
  5. Osoba z kontem: wskażcie encję, która ma pole typu UserAccount (R2.06).
  6. Moduły: pogrupujcie tabele w co najmniej 2 moduły (pakiety), np. seating i booking (R2.03). Jedno słowo, małe litery, po angielsku.
  7. Podział: przy każdej tabeli imię osoby, która ją napisze. Encja łącząca i encja wskazująca na konto powinny trafić do różnych osób niż tabele, na które wskazują, żeby każda osoba napisała co najmniej jedną relację.

E3. Encja bez relacji

New → Java Class → CafeTable w seating.domain (nazwa Table jest zajęta przez adnotację JPA):

package pl.wsb.kawiarnia.seating.domain;

import jakarta.persistence.*;

@Entity
@Table(name = "cafe_table")
public class CafeTable {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "number", nullable = false, unique = true)
    private Integer number;

    @Column(name = "seats", nullable = false)
    private Integer seats;

    @Column(name = "room", nullable = false, length = 40)
    private String room;

    protected CafeTable() {
    }

    public CafeTable(Integer number, Integer seats, String room) {
        this.number = number;
        this.seats = seats;
        this.room = room;
    }

    // gettery: Code → Generate… → Getter → zaznaczcie wszystkie pola
}

Konstruktor i gettery generuje IntelliJ: Code → Generate… (macOS ⌘N, Windows Alt+Insert). Setterów nie generujcie: stan encji będą zmieniać metody biznesowe (LAB 04). Po Rerun w logu pojawia się:

create table cafe_table (
    number integer not null unique,
    seats integer not null,
    id bigint generated by default as identity,
    room varchar(40) not null,
    primary key (id)
)

E4. Encja z relacją do konta (@ManyToOne)

Guest w booking.domain: dane gościa, powiązane z kontem logowania.

@Entity
@Table(name = "guest")
public class Guest {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "full_name", nullable = false, length = 80)
    private String fullName;

    @Column(name = "phone", length = 20)
    private String phone;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "user_account_id")
    private UserAccount account;               // import pl.wsb.kawiarnia.account.domain.UserAccount

    protected Guest() {
    }

    public Guest(String fullName, String phone, UserAccount account) { … }

    // gettery
}

W logu, oprócz create table guest z kolumną user_account_id bigint, pojawia się klucz obcy:

alter table if exists guest
   add constraint FKd9rr1jsx25ybl6bf1nl12ywhq
   foreign key (user_account_id)
   references user_account

fetch = FetchType.LAZY oznacza, że konto jest doczytywane z bazy dopiero przy pierwszym użyciu, a nie razem z gościem. Dla @ManyToOne dopisujcie to zawsze; dlaczego to ważne, zobaczycie na LAB 03 przy problemie N+1.

E5. Encja ze statusem, kwotą i dwiema relacjami

Reservation w booking.domain: obiekt z cyklem życia.

@Entity
@Table(name = "reservation")
public class Reservation {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "guest_id", nullable = false)
    private Guest guest;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "table_id", nullable = false)
    private CafeTable table;                   // import pl.wsb.kawiarnia.seating.domain.CafeTable

    @Column(name = "starts_at", nullable = false)
    private LocalDateTime startsAt;

    @Column(name = "party_size", nullable = false)
    private Integer partySize;

    @Enumerated(EnumType.STRING)
    @Column(name = "status", nullable = false, length = 20)
    private ReservationStatus status;

    @Column(name = "deposit", nullable = false, precision = 10, scale = 2)
    private BigDecimal deposit;

    protected Reservation() {
    }

    public Reservation(Guest guest, CafeTable table, LocalDateTime startsAt, Integer partySize, BigDecimal deposit) {
        this.guest = guest;
        this.table = table;
        this.startsAt = startsAt;
        this.partySize = partySize;
        this.status = ReservationStatus.NEW;   // nowa rezerwacja zawsze zaczyna od NEW
        this.deposit = deposit;
    }

    // gettery
}

Zwróćcie uwagę na DDL: status enum ('CANCELLED','CONFIRMED','DONE','NEW') (tekst, nie liczba) i deposit numeric(10,2). Z double byłoby float(53), czyli zaokrąglenia przy każdym dodawaniu.

E6. Encja łącząca: relacja wiele-do-wielu

Rezerwacja może mieć wiele dodatków (tort, kwiaty), a dodatek trafia do wielu rezerwacji. Para ma atrybut (ilość), więc zamiast @ManyToMany powstaje encja ReservationExtra z dwoma polami @ManyToOne. Najpierw słownik Extra (id, name, price jako BigDecimal), potem:

@Entity
@Table(name = "reservation_extra",
        uniqueConstraints = @UniqueConstraint(columnNames = {"reservation_id", "extra_id"}))
public class ReservationExtra {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "reservation_id", nullable = false)
    private Reservation reservation;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "extra_id", nullable = false)
    private Extra extra;

    @Column(name = "quantity", nullable = false)
    private Integer quantity;

    protected ReservationExtra() {
    }

    public ReservationExtra(Reservation reservation, Extra extra, Integer quantity) { … }

    // gettery
}

uniqueConstraints pilnuje, żeby ten sam dodatek nie trafił dwa razy do jednej rezerwacji. W DDL: unique (reservation_id, extra_id).

E7. Strona odwrotna (@OneToMany), opcjonalnie

Jeśli chcecie przejść od stolika do listy jego rezerwacji, dopiszcie w CafeTable:

@OneToMany(mappedBy = "table")
private List<Reservation> reservations = new ArrayList<>();

mappedBy = "table" to nazwa pola @ManyToOne w Reservation. Bez mappedBy Hibernate utworzyłby dodatkową tabelę cafe_table_reservations, której nie planowaliście (R2.09). W DDL nic nie przybywa: to tylko widok z drugiej strony.

ZadanieF · Dane startowe i konsola H2

F1. data.sql

Hibernate tworzy tabele od nowa przy każdym starcie, a potem Spring Boot wykonuje src/main/resources/data.sql. Każda osoba wypełnia swoje sekcje (C3). Zasady:

  • Kolejność: najpierw tabele, na które wskazują klucze obce (stoliki i goście przed rezerwacjami, rezerwacje przed dodatkami do rezerwacji).
  • Identyfikatory: nie wpisujecie id; baza numeruje wiersze od 1 w kolejności wstawiania. W kluczach obcych używacie tych numerów. Konta demo z szablonu mają id 1–4, więc konta zespołu dopisane po nich to 5, 6, 7.
  • Nazwy kolumn dokładnie jak w @Column(name) i @JoinColumn(name); enumy jako tekst w apostrofach; daty jako '2026-11-14 18:00:00'.
  • 2–3 wiersze na tabelę, sensowne dla Waszego pomysłu. Reguła R2.10 wymaga co najmniej jednego w każdej tabeli.

F2. Sprawdzenie w konsoli H2

Po Rerun otwórzcie http://localhost:8080/h2-console (JDBC URL jdbc:h2:file:./data/wdtb, użytkownik sa, hasło puste). Po lewej stronie jest lista tabel: rozwińcie swoją i porównajcie kolumny ze schematem z części D. Wykonajcie:

select * from reservation;

select r.id, g.full_name, t.number as table_no, r.starts_at, r.status
from reservation r
join guest g on g.id = r.guest_id
join cafe_table t on t.id = r.table_id;

Drugie zapytanie łączy trzy tabele kluczami obcymi: tak baza „widzi” Wasze relacje. Na LAB 03 to samo napiszecie w JPQL.

Komunikat w logu Przyczyna i poprawka
Referential integrity constraint violation klucz obcy wskazuje wiersz, którego jeszcze nie ma: zła kolejność sekcji w data.sql albo zły numer id
Column "…" not found nazwa kolumny w insert różni się od @Column(name) / @JoinColumn(name)
Table "…" not found klasa bez @Entity albo poza pakietem pl.wsb.<projekt>; inna nazwa w @Table(name)
NULL not allowed for column "…" kolumna z nullable = false pominięta w insert
Unique index or primary key violation dwa wiersze z tą samą wartością kolumny unique (np. numer stolika)
No default constructor for entity brak konstruktora protected <Klasa>() {}
Port 8080 was already in use poprzednie uruchomienie wciąż działa: czerwony kwadrat w oknie Run

Błąd w data.sql zatrzymuje start aplikacji, więc czerwone są też R1.02 i R2.10. Czytajcie log od pierwszej linii z Caused by: tam jest nazwa tabeli i kolumny.
