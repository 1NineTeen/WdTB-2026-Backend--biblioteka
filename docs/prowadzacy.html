Dla prowadzącego: konfiguracja GitHub

Szablon

  1. Repozytorium szablonu: wkoszela/WdTB-2026-Backend--projectname-, publiczne.
  2. W .github/workflows/ci.yml zmienna RULES_REPO wskazuje szablon (wkoszela/WdTB-2026-Backend--projectname-).
  3. Opcja Template repository nie jest potrzebna: zespoły forkują szablon.

Nie są potrzebne GitHub Classroom ani GitHub Education: publiczne repozytoria mają GitHub Actions bez limitu minut.

Repozytoria zespołów (forki)

  • Osoba hostująca forkuje szablon na swoje konto i zmienia nazwę forka na WdTB-2026-Backend-<nazwaprojektu> (instrukcja krok po kroku: LAB 01, część B).
  • W forku trzeba raz włączyć GitHub Actions (zakładka Actions).
  • Settings → Collaborators: zespół i prowadzący. Wszystkie forki widać też w Insights → Forks szablonu.
  • Nazwa projektu i link do repozytorium trafiają do arkusza zespołów (zakładka grupy). Arkusz sprawdza, czy link zawiera WdTB-2026-Backend-<nazwa projektu>.
  • W repozytorium nie ma danych osobowych poza loginami GitHub i imionami w PROJEKT.md. Numery indeksu i e-maile są tylko w arkuszu.
  • Nowe instrukcje zespoły pobierają przyciskiem Sync fork (reguły workflow i tak pobiera z szablonu).

Jak działa sprawdzanie

  • Workflow Testy i reguły uruchamia się przy każdym pushu na main, każdym Pull Requeście i każdym tagu lab-*.
  • Numer laboratorium bierze się z tagu: tag lab-2 uruchamia reguły LAB 02, tag lab-3-poprawa reguły LAB 03. Przy pushu i PR obowiązuje <lab> z pom.xml.
  • Przed testami workflow pobiera oficjalne reguły z szablonu i nadpisuje nimi src/test/java/pl/wsb/rules. Lokalne „poprawki” reguł nie mają wpływu na wynik.
  • Wynik: zakładka Actions → przebieg dla tagu → Summary. Jest tam tabela reguł (✅ / ❌ / pominięte) z listą rzeczy do poprawy oraz raport wkładu członków zespołu od poprzedniego tagu.
  • Ręczne uruchomienie z innym numerem labu: Actions → Testy i reguły → Run workflow, pole „Numer laboratorium”.

Zespół może zmodyfikować plik workflow. Jeśli masz wątpliwości, uruchom reguły sam:

git clone https://github.com/<login>/WdTB-2026-Backend-<nazwa>.git && cd WdTB-2026-Backend-<nazwa>
git checkout lab-N
rm -rf src/test/java/pl/wsb/rules && cp -r <szablon>/src/test/java/pl/wsb/rules src/test/java/pl/wsb/
mvn verify -Dlab=N

Ocena labu (na koniec zajęć, ok. 5 min na zespół)

  1. Przebieg Testy i reguły dla tagu lab-N jest zielony.
  2. Raport Wkład członków zespołu: czy każda osoba ma commity i zmergowany Pull Request, kto robił recenzje.
  3. Losowa osoba, losowa linia z Pull Requesta innej osoby: „co to robi?”, „dlaczego tak?”, „zmień X na Y”.
  4. Pytanie kontrolne z instrukcji labu (dla 5.0).
  5. Wpis oceny do własnego arkusza ocen (arkusz zespołów jest wspólny ze studentami).

LAB 07: odrabianie

Poprawki zespołów oceniaj z nowych tagów, np. lab-3-poprawa: workflow sam uruchomi reguły LAB 03.

Zmiany wymagań (opcjonalnie, LAB 05)

Przykłady do losowania: ceny w wielu walutach · usunięcie konta (RODO) · soft delete · druga rola użytkownika (np. firma zamiast osoby) · zamówienie grupowe · historia zmian statusu.
